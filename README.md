# STAY BUT 성수 — 숙소 운영 어드민

게스트하우스 운영에 필요한 예약·청소·정산·손님 응대를 한 곳에서 처리하는 자체 제작 PMS입니다.
빌드 도구 없이 **단일 HTML 파일 + Supabase**로 동작하며, GitHub Pages로 배포합니다.

**운영 중** · 객실 5실 (101 · 102 · 201 · 202 · 301) · 채널 3곳 (부킹닷컴 · 에어비앤비 · 아고다)

## 무엇을 해결하는가

상주 인력 없이 5실을 운영하면서 생기는 문제를 자동화했습니다.

| 문제 | 해결 |
|---|---|
| 채널 3곳의 예약을 각각 로그인해서 확인 | 예약 메일을 자동 파싱해 한 목록으로 |
| 수수료율이 채널·시점마다 달라 정산액을 모름 | 채널별 요율 규칙 테이블 + 자동 계산 |
| 청소 배정·정산을 수기로 관리 | 예약 저장 시 청소 작업 자동 생성, 주간 정산 자동 집계 |
| 손님 문의 대응 (다국어) | 객실 QR → 웹 채팅, 자동 번역 |
| 매출을 팀에 보고할 자료를 매번 수기 작성 | 매출 인사이트 화면 + 엑셀·이미지 내보내기 |
| 재고를 세러 갈 수 없음 | 비품은 구매일만 기록, 평균 주기로 시점 추정 |

## 시스템 구성

```
      채널 예약 메일                        손님 (객실 QR)
   부킹닷컴 · 에어비앤비 · 아고다                  │
            │                                    │
            ▼                                    ▼
    Google Apps Script                      손님용 채팅 화면
     (10분 주기 파싱)                              │
            │                                    │
            └──────────►  Supabase  ◄────────────┘
                      (PostgreSQL · RLS)
                            ▲
                            │
              ┌─────────────┴─────────────┐
              │                           │
          어드민 화면                호스트 채팅 콘솔
        (운영자 · PC/모바일)            (응대 · 웹푸시)
```

- **예약은 메일에서 자동으로** 들어옵니다. 채널 사이트에 로그인하지 않습니다
- **청소 작업은 예약이 저장될 때 자동 생성**됩니다
- **손님 채팅은 예약 데이터와 연결**되어 있어, 응대할 때 객실·일정·인원·채널이 자동으로 보입니다

## 설계 결정

기능보다 **왜 이렇게 만들었는지**가 나중에 더 필요한 기록이라 남깁니다.

### 빌드 도구를 쓰지 않았다

운영자가 개발자가 아닙니다. React·npm·빌드 파이프라인을 넣으면 그 순간부터 개발자 없이는 손을 못 댑니다.
파일 하나 덮어쓰면 배포가 끝나는 구조여야 실제로 유지됩니다.

### 채팅을 어드민에 넣지 않고 분리했다

어드민 본체는 이미 큽니다. 상담 UI까지 넣으면 로딩이 무거워지고, 상담은 응대 중에만 쓰는 화면입니다.
어드민에는 **링크와 미확인 배지만** 두고, 실제 채팅은 경량 페이지로 분리했습니다.

### 챗봇을 만들지 않고 실시간 상담만 만들었다

객실 5개 규모에서 챗봇은 오답을 낼 위험이 실익보다 큽니다. 사람이 직접 답하고, **번역만 자동화**했습니다.

### 재고 숫자를 포기했다

처음엔 재고 카운트를 넣었는데, 상주하지 않으니 아무도 세지 않았습니다.
초기값 5가 몇 달째 그대로 남아 오히려 오해를 만들었습니다.
그래서 **"언제 샀나"만 기록**하고, 두 번 이상 구매하면 평균 주기를 계산해 시점을 추정하는 방식으로 바꿨습니다.

### 어드민이 훈수를 두지 않게 했다

한때 "202호를 10% 올리면 월 98만원"처럼 권고안을 띄웠습니다.
컨설팅 자료로는 맞지만 매일 보는 화면에서는 노이즈였습니다.
지금은 **"지금 어떤 상태인가"만 보여주고 판단은 운영자가** 합니다.

### 지표의 분모를 하나로 통일했다

`ADR`과 `점유율`이 서로 다른 박수를 분모로 쓰고 있어 `ADR × 점유율 ≠ RevPAR` 이었습니다.
숫자 셋이 서로 안 맞으면 보는 사람이 화면 전체를 못 믿습니다.
분모를 통일하고, **화면에서 항등식을 자동 검산**해 어긋나면 빨간색으로 표시합니다.

### 경고에 「확인함」을 붙였다

이상 데이터 감지를 만들었더니 의도된 건(환불 처리 등)이 매일 경고로 떴습니다.
그러면 결국 아무도 안 봅니다. 확인한 건은 목록에서 빠지게 했습니다.

## 화면 구성

### 대시보드
오늘 입실·퇴실·재실, 확인이 필요한 항목, 최근 들어온 예약.

### 예약관리
조회 조건(기준일자 · 목록보기 · 기간 · 채널 · 상태)을 정하고 상세내역을 봅니다.

- **기준일자** — 체크인일 / 체크아웃일 / 예약일 중 선택. 어떤 기준으로 집계했는지가 화면에 항상 표시됩니다
- **목록보기** — 예약건별 / 일자별 / 객실별. 같은 조건을 세 가지로 집계
- 객실 타임라인 — 예약 하나가 막대 하나. 채널은 왼쪽 색띠, 숙박중은 초록 점
- 수수료·정산액 컬럼 포함 → 채널 명세서 대조를 어드민에서 처리

### 매출 인사이트
카드 14개로 구성. 위에서 아래로 *얼마 벌었나 → 어디서 → 언제 → 뭐가 새는가* 순서입니다.

- **핵심 지표** — 거래액 · 예약건수 · 예약박수 · 실제숙박/공실 · ADR · 점유율 · RevPAR
  - `ADR × 점유율 = RevPAR` 항등식을 화면에서 자동 검산합니다
  - 진행 중인 달에는 전월 대비 증감률을 표시하지 않습니다 (아직 파는 중이라 비교가 성립하지 않음)
- **수수료 · 실수령률** — 채널별 수수료율과 **박당 실수령**
  - 수수료율이 가장 낮은 채널이 실제로는 가장 덜 남는 경우가 있습니다. ADR이 낮으면 수수료를 덜 떼도 손에 남는 돈이 적습니다. 그래서 두 지표를 함께 봅니다
- **가격대별 판매 분포** — 어느 요금 구간이 가장 많이 팔렸는지. 가격 조정의 근거
- **월별 추이** — 지난 달까지 실선, 이번 달부터 점선. 판매가 진행 중인 달을 완료된 달처럼 비교하지 않기 위해서입니다
- 채널별 · 평일주말 · 객실별 · 취소 · 요일별 · 리드타임 · 국적 · 판매일보

### 청소관리
주간 보드에서 객실별 청소를 배정하고, 실장님별 주간 정산을 자동 집계합니다.
상태는 **담당 미정 / 배정 완료** 두 가지만 봅니다 — 배정됐는지가 핵심이라서입니다.

### 비품관리
재고 숫자를 세지 않고 **마지막 구매일**만 기록합니다.

- 오래 안 산 품목이 위로 올라옵니다
- 두 번 이상 구매하면 **평균 구매 주기**가 자동으로 잡혀 "보통 30일마다 사는데 44일 됐다"를 알려줍니다
- 체크로 담아 한 번에 기록 · 소모품 / 내구재 분리

### 동기화 · 점검
메일 파서가 처리한 기록과, 확인이 필요한 데이터를 모아 봅니다.

- **이상 감지** — 금액 0원 · 객실 미배정 · 수수료율 이상 · 수수료 미확정 · 취소인데 수수료 남음 · 중복 예약
- **「확인함」** 처리 — 의도된 건을 계속 경고하지 않도록
- 메뉴에 미확인 건수 배지 표시

### 손님용 · 호스트용 채팅
객실 QR로 접속하는 손님 화면과, 호스트가 응대하는 콘솔.

- 예약 1건 = 대화방 1개. 같은 방 손님 여러 명이 각자 폰으로 들어와도 한 대화방을 공유
- 유효기간은 **체크인일 16:00 ~ 퇴실일 12:00**. 퇴실 후에는 접근 차단
- 채널명·일정·인원이 예약 데이터에서 자동으로 붙습니다
- 7개 언어 · 자동 번역 · 사진 전송 · 빠른답변 · 읽음표시
- 손님 메시지가 오면 **웹푸시**로 담당자 휴대폰에 알림

## 배포

빌드가 없습니다. 파일을 덮어쓰면 끝입니다.

1. 저장소에 같은 파일명으로 업로드 (`index.html` 등)
2. GitHub Pages가 1~2분 내 자동 반영
3. 브라우저 강력 새로고침 (`Ctrl+Shift+R`)

수정 후에는 아래를 확인합니다.

- 인라인 `<script>` 문법 검사
- 모바일 뷰 (iOS 사파리 포함) — 가로 잘림이 자주 생기는 지점입니다
- 지표 검산 줄이 `✓ 일치`로 뜨는지

## 개발 규칙

### DB 스키마 함정

**자동계산 컬럼에 값을 넣으면 안 됩니다.**

- `bookings.nights` = `checkout_date - checkin_date`
- `bookings.net_amount` = `gross_amount - COALESCE(channel_commission, 0)`

수수료를 반영하려면 `channel_commission`을 수정합니다. `net_amount`를 직접 UPDATE하면 에러가 납니다.

**컬럼명 주의**

- `bookings` → `booking_status`
- `cleaning_tasks` · `supply_orders` → `status`

**배제 제약** — 같은 객실에 기간이 겹치는 예약이 들어가지 않도록 DB 차원에서 막혀 있습니다. 오버부킹은 화면 검증이 아니라 DB 제약으로 방지합니다.

### 색상 · 톤

`:root`에 정의된 CSS 변수만 사용합니다. 하드코딩 금지.

- 브랜드 · 강조 `--accent` (웜 그레이 계열 근검정)
- 초록 · 빨강은 **의미가 있을 때만** — 정상/경고, 달성/미달, 확정/취소
- 채널 색(부킹닷컴 · 에어비앤비 · 아고다)은 OTA 브랜드색이라 예외

### 화면 원칙

- 훈수 두지 않습니다. "지금 어떤 상태인가"만 보여주고 판단은 운영자가 합니다
- 지표는 분모를 통일합니다. 서로 안 맞는 숫자가 한 화면에 있으면 전체를 못 믿습니다
- 진행 중인 기간과 완료된 기간을 섞어 비교하지 않습니다

## 자주 겪은 버그 패턴

증상만 보면 원인을 못 찾는 것들입니다.

| 증상 | 진짜 원인 |
|---|---|
| 캘린더 날짜가 하루 밀림 / 말일 누락 | `toISOString()`이 UTC로 변환해 KST 기준 하루를 당김 → 로컬 문자열로 직접 조립 |
| 예약이 "안 들어감" | 저장은 됐고 표시·필터 문제인 경우가 많음 → DB부터 직접 확인 |
| 버튼 클릭 무반응, 에러도 없음 | `<div>` 짝이 안 맞아 보이지 않는 요소가 버튼을 덮음 |
| 로드 후 기능 전체 먹통 | 쿼리 컬럼명 오류로 400 에러 → 그 뒤 JS 전부 정지 |
| 화면 오른쪽이 잘림 | flex/grid 자식에 `min-width: 0`이 없어 오버플로우 |
| 지표가 서로 안 맞음 | 분모가 다름 (예약 기준 vs 실제 점유 기준) |
| 채널 취소 알림이 "예약 없음"이라고 뜸 | 취소 메일이 예약 등록 메일보다 먼저 처리됨. 또는 채널이 번호를 새로 발급 |

## 매출 집계 기준

**체크인 기준**(발생주의)이 기본입니다. 회계팀 정산 자료와 맞추기 위해서입니다.

거래액·ADR·RevPAR는 **"기준일이 그 기간인 예약"의 박수**를 같은 분모로 씁니다. 그래서 `ADR × 점유율 = RevPAR`이 정확히 성립합니다.

**예약 박수와 실제 숙박은 다릅니다.**

- **예약 박수** — 그 달 체크인한 예약의 총 박수. 다음 달에 묵는 밤도 포함
- **실제 숙박** — 그 달에 실제로 묵은 밤

달을 걸쳐 묵는 예약이 있으면 두 숫자가 벌어집니다. 화면에 둘 다 표시하고 공실도 함께 보여줍니다.

**수수료**

- 채널별·시점별로 요율이 다릅니다. 요율 규칙을 테이블로 관리하고 예약 저장 시 자동 반영합니다
- 프로모션이 들어간 건은 일괄 요율이 맞지 않아 **명세서 금액을 그대로** 씁니다
- **취소건은 수수료 0원**입니다. 채널이 취소에 수수료를 부과하지 않습니다
- 여러 객실을 한 번에 결제한 예약은 수수료를 **거래액 비율로 배분**합니다
